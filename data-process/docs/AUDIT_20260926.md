## 四、decontam 事故与修复（E-22）

- **现象**：表面 7,050/12,828 分片有 summary，实际 4,668 是 error（fineweb 3,769/3,987 全灭）；error_message = KeyError('the') 等高频词
- **根因**：`word_hashes` 先算 missing 再 clear 缓存的时序 bug（详见工程经验记录 E-22）
- **修复**：clear 时 missing 扩为全批词；回归测试锚定；真实失败分片重跑验证通过
- **重启后监控**：20 分钟窗口 95 分片 0 error；截至 20:14 进度 3,400/12,828，**ETA ~12h**（fineweb 大分片区 0.25 shards/s，后续 github-code/starcoderdata 类似量级）
- **吞吐修正**：fineweb 型大分片实测 ~300 行/s/核（非 README 的 6.9k——那是合成/小分片基准），全池 ETA 按 12-24h 规划

## 五、S4 打分轨红灯（S6 物化的真实阻塞）

- **CV 未过门**：留一源 mean AUC **0.821 < 0.85**，wikipedia-zh fold 仅 0.624（语言偏置实锤）。注意当前 `cv_metrics.json` 是 wordNgrams=2 旧版；14:42 重训的 ngrams=3 版**未复检 CV**
- **分数分布证据**：fineweb fasttext p50=0.024（近乎判全池垃圾）；cci3-hq fasttext p50=0.002（中文系统性低分，靠 upstream_norm 撑）；automathtext bert_score 饱和（p25=1.0）
- **goldset 缺陷**：`edu-low-tail` 负样本采到 **0 条**（规则失败未修）；dolma-books 正样本 quota 缺口 37%
- **结论**：s4_scored 现有 6 源产物**不可用于生产选取**；S6 硬门①会正确拒绝
- **收尾路径**（建议顺序）：修 edu-low-tail 规则 → 负样本扩分层尾部（low/mid/high 分位）→ ngrams=3 复检 CV（目标 mean≥0.85 且 zh≥0.75）→ 17 源全量重打分 → 分位表。fasttext 单核训练 ~54min，全量打分 IO 密集（与 decontam 排队）

### 10.1 S4 打分轨三连坑修复（E-25）

|---|---|---|
| edu-low-tail 采 0 条 | `upstream_max=1.0` 脱离 fineweb-edu 实际分布（下限 2.5，edu≥3 筛选子集） | 阈值改 2.69（实际 p25，先 `np.percentile` 标定再写配置） |

### 10.2 qa 域 HTML 残留清洗（E-26）

stack-exchange 正文残留 `<p>`/`<a>`/实体（html_tag_ratio 对低密度残留是盲区）。`detectors.clean_for_domain`：qa 域 strip + unescape（code/math 不动，`&amp;` 是语义内容），检测与写出同源。398 分片 S1→S2→S3 重刷（趁 decontam 未跑到，下游零波及）。回归测试 3 项锚定。

### 10.3 S6 归并内存预算守卫

逐域归并峰值 ≈ 候选行 × ~120B（npz 全载 + concatenate 翻倍 + lexsort 3 键）。web 域预估 1.1B 候选 × 120B ≈ 130GB——可承受但贴线。加 fail-fast 守卫（MERGE_MEMORY_BUDGET=500GB，超限提示分域物化）。`tests/test_materialize.py` 7 项全过。
